# 6. 互換ツールの実装ガイド

純正 Fuel Manager の代わりになるツールを作るための指針です。参照用のコードは [`examples/`](../examples) にあります。

> [!WARNING]
> 参照コードとテストは、この解析から推定したプロトコルで動く**なりすまし i-Map** を相手に確かめただけです。**実機では一度も試していません。** テストが通っても、本物の i-Map との互換性が保証されるわけではありません。実機で使うときは [6.6 節](#66-実機で初めて試すときの手順)の手順に従い、自己責任で行ってください。

## 6.1 基本方針

1. **送るバイト列は純正とまったく同じにする。** 本体側の作りがわからないので、「それでも受け付けるだろう」という形に変えるのは避けます。たとえば、書き込み時に最後の値のあとに付くカンマ、列ごとの `/`、最後の列のあとは応答を待たないこと、なども純正どおりにします。
2. **受け取るときは寛容にする。** 純正の弱点（末尾の1文字でしか終わりを判定しない、待ち時間が無制限）は直し、多少違う形のデータでも安全に扱えるようにします。
3. **書き込む前の検査と、書いたあとの確認を足す。** 純正の UI では作れないデータは送らないようにし、書いたあとは読み戻して比べます。

## 6.2 環境

| 項目 | 推奨 |
|---|---|
| 言語とライブラリ | Python 3.8 以上と [pyserial](https://pypi.org/project/pyserial/)。Windows、macOS、Linux で同じコードが動く |
| ドライバ | Linux はカーネル標準の `cp210x` ドライバ。Windows と macOS では、必要なら Silicon Labs の CP210x VCP ドライバを入れる |
| ポート名 | Windows：`COM4` など。Linux：`/dev/ttyUSB0` など。macOS：`/dev/cu.SLAB_USBtoUART` や `/dev/cu.usbserial-XXXX` など |
| 回線設定 | 38400 bps、8N1、フロー制御なし |

純正ケーブルの代わりに汎用の USB シリアル変換モジュールを使う場合は、[7 章](07-pc-interface-cable.md)の注意点を先に読んでください。

### ケーブルを見つける

純正のように「開けたポート」を選ぶのはやめて、USB の VID/PID で探します。CP210x の工場出荷時の値は `10C4:EA60` です。ただし、KITACO のケーブルがこの値のままかどうかは【不明】です。最初はデバイスマネージャや `lsusb` で実際の値を確かめてください。

```python
from serial.tools import list_ports

def find_cable(vid=0x10C4, pid=0xEA60):
    hits = [p.device for p in list_ports.comports() if (p.vid, p.pid) == (vid, pid)]
    if len(hits) != 1:
        raise RuntimeError(f"ケーブルを 1 本に絞れない: {hits}")
    return hits[0]
```

## 6.3 参照実装（[`examples/imap_ref.py`](../examples/imap_ref.py)）

| 関数 | 内容 |
|---|---|
| `read_map(port)` | `m` を送り、`(マップ番号, 30 列 × 21 個の生の値)` を返す |
| `write_map(port, cols)` | 検査してから `s` を送り、30 列を書き込む |
| `parse_fmp_text(text)` / `to_fmp_text(cols)` | `.fmp` 形式との相互変換。書き出しは純正と同じ末尾（CRLF 3 つ）にする |
| `validate(cols)` | 書き込む前の検査（[6.5 節](#65-書き込む前の検査)） |
| `rev_limit(cols)` | レブリミットの回転数を求める |

値はすべて**生の値**（補正率 + 100、リミットより上は 0）で扱います。画面に出す値に直すときは 100 を引きます。

### 読み出し

```python
def read_map(port, first_timeout=20.0, idle_timeout=5.0):
    with open_port(port) as s:
        s.reset_input_buffer()
        s.write(b"m")
        deadline = time.monotonic() + first_timeout
        map_no = None
        while map_no is None:
            if time.monotonic() > deadline:
                raise TimeoutError("'m' に対する応答がない")
            b = s.read(1)
            if b and b != b"\x00":
                map_no = b[0]  # 生のバイト値
        buf = bytearray()
        last_rx = time.monotonic()
        while b"/" not in buf:  # 純正は末尾の 1 文字しか見ないが、ここでは途中の "/" も検出する
            chunk = s.read(4096)
            if chunk:
                buf += chunk
                last_rx = time.monotonic()
            elif time.monotonic() - last_rx > idle_timeout:
                raise TimeoutError("マップデータの受信が途中で止まった")
        return map_no, parse_fmp_text(buf[: buf.index(b"/")].decode("ascii"))
```

純正では、マップデータを受け取る間の待ち時間に上限がありません。ここでは「最後に受信してから `idle_timeout` 秒」で打ち切ります。本体が送り終えるまでにかかる時間は【不明】なので、実機では余裕を持った値から始めてください。

### 書き込み

```python
def write_map(port, cols, ack_timeout=20.0):
    validate(cols)
    with open_port(port) as s:
        s.reset_input_buffer()
        s.write(b"s")
        wait_for(s, b"r", ack_timeout)          # r 以外は読み捨てる（純正と同じ）
        for c, col in enumerate(cols):
            s.write(("".join(f"{v}," for v in col) + "/").encode("ascii"))
            s.flush()
            if c != NUM_COLS - 1:               # 純正は最後の列のあと応答を待たない
                wait_for(s, b"r", ack_timeout)
```

純正は値を1つずつ `Write` で送っていますが、ここでは1列分をまとめて送ります。線上に流れるバイトの並びは同じです。ただ、USB で送るときのパケットの区切り方は変わります。本体の受信バッファが小さい場合に違いが出る可能性は残ります【推測】。

### 書き込みのあとの待ち時間

最後の列のあと、本体からは応答がありません（少なくとも純正は待っていません）。なりすまし i-Map を使ったテストでも、`write_map` から戻った時点では最後の列がまだ処理し終わっていませんでした。実機でも本体の書き込みが終わる前に次の操作に移ってしまうおそれがあるので、**書き込みのあとは少し間を空けてから**読み戻しや電源断をしてください。必要な時間は【不明】です。

## 6.4 なりすまし i-Map でのテスト（[`examples/imap_emulator.py`](../examples/imap_emulator.py)）

疑似端末（pty）の片側で、[4 章](04-serial-protocol.md)のプロトコルどおりに応答する `FakeIMap` を動かします。もう片側のポート名（`dev.port`）を参照実装に渡すと、実機がなくても読み出しと書き込みを通しで試せます。

```bash
pip install pyserial
cd examples
python test_roundtrip.py                                  # 説明用マップでの往復テスト
python test_roundtrip.py "125cc STD GPR TYPE1 CAM.fmp"    # 公式配布マップの解析も試す
```

実行例（2026-10-20、Linux、Python 3.12、pyserial 3.5）：

```text
読み出し OK: map_no 7 rev_limit 12000
書き込みと読み戻し OK: rev_limit 11000
検査 OK（リミット 5000rpm）: レブリミットは 9000rpm 以上でなければならない（純正 UI の制約）

```

なりすまし i-Map には、本文で【推測】とした点も含めて、この解析の前提がそのまま入っています。たとえば、読み出しデータの改行は CRLF で、`/` のあとには何も送らない、としています。実機の動作が違えば、そこに合わせて直す必要があります。

## 6.5 書き込む前の検査

`validate()` が弾くデータは次のとおりです。純正の UI では作れないデータを送らないためのものです。

| 検査 | 理由 |
|---|---|
| 30 列 × 21 値 であること | プロトコルの前提 |
| 0 以外の値は 60〜140 | 純正の UI の入力範囲（−40〜+40%） |
| 1 つの列に 0 と 0 以外が混ざっていない | 純正はリミットより上の列を全部 0 にして出力する |
| 全部 0 の列は、リミットより上にまとまっている | 同上 |
| レブリミットが 9000 rpm 以上 | 純正の UI の下限（[2.7 節](02-software-structure.md#レブリミットの設定)） |

本体が範囲外の値をどう扱うかは【不明】です。「純正で作れるデータしか送らない」を守ってください。

## 6.6 実機で初めて試すときの手順

取扱説明書の注意（26〜28 ページ）に加えて、次の順で進めることを勧めます。

1. **電源を安定させる。** バッテリーの電圧を確かめるか、できれば安定した 12V 電源を使います。通信中に電源が切れると本体が壊れるおそれがあります。
2. **エンジンは止めたまま**、メインキーを ON にします。
3. **読み出しだけを試す。** DIP スイッチの位置ごとに読み出し、`.fmp` として保存します。これがバックアップになります。返ってきたマップ番号が、[4.4 節](04-serial-protocol.md#マップ番号と-dip-スイッチの対応)の計算式と合うかも確かめます。ユーザーオリジナルマップ（DIP 全部 ON の MAP16）は、一度も書き込んでいなければ読み出せません。
4. **純正ソフトと比べる。** 可能なら、同じマップを純正 Fuel Manager でも読み出して保存し、内容がバイト単位で一致するか確かめます。
5. **最初の書き込みは、内容を変えずに書き戻す。** ユーザーオリジナルマップのバックアップを、そのまま書き込みます。まだ書き込んだことがなければ、MAP1（補正値なし）を読み出したものを書き込むのが無難です。
6. **読み戻して比べる。** DIP スイッチを全部 ON（MAP16）にして読み出し、書いた内容と一致するか確かめます。
7. ここまで問題がなければ、小さな変更から試します。

各手順で、送ったバイトと受け取ったバイトをすべて時刻付きで記録しておくと、問題が起きたときに原因を追いやすくなります。

## 6.7 純正の不具合への対応

| 純正の問題（[5 章](05-quirks-and-bugs.md)） | 互換ツールでの対応 |
|---|---|
| 5.1・5.2 COM20 が使えない、自動検出で接続先を確かめない | VID/PID で探す。ポートは明示的に指定できるようにする |
| 5.3 最初の Write が空振りする | ポートを見つけたらそのまま処理を続ける |
| 5.4・5.5 通信が途切れると固まる | どの段階にもタイムアウトを付ける。途中の `/` も検出する |
| 5.6 エラー表示がまぎらわしい | タイムアウト、解析エラー、ポートのエラーを区別して表示する |
| 5.7 一時ファイル | 使わない（メモリ上で解析する） |
| 5.8 書き込みを確かめていない | 読み戻して比べる機能を付ける |
| 5.10〜5.13 ファイル読み込みが甘い | 30 × 21 以外や範囲外の値はエラーにする（`validate`） |

## 6.8 実機で確かめたいこと

[4.7 節](04-serial-protocol.md#47-わかっていないこと)の不明点は、次の方法で確かめられます。

- **純正ソフトの通信を傍受する。** Windows で純正 Fuel Manager を動かし、シリアルポートモニタ（ソフトウェア）や USB プロトコルアナライザで送受信のバイト列と時刻を記録します。次の点がわかります。
  - 読み出しデータの改行コード
  - `/` のあとに何か来るか
  - 最後の列のあとに `r` が来るか
  - 列ごとの応答にかかる時間
- **ケーブルの UART 側を観測する。** ロジックアナライザを UART の信号線につなげば、ドライバや OS の影響を受けない生の信号を確かめられます。
