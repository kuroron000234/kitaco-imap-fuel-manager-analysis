# 5. 既知の不具合と癖

デコンパイルしたコードから見つかった、純正 Fuel Manager の不具合と癖です。いずれもコードを読んで確かめたもの【観測】で、実際に Windows で動かして再現したわけではありません。互換ツールを作るときに同じ問題を持ち込まないための参考にしてください。

## 通信まわり

### 5.1 COM20 が使えない

`"COM20"` を「ポート未設定」の目印に使っています。そのため、COM メニューで COM20 を選んでも、Read や Write のたびに自動検出（`Open_port`）が動きます。ケーブルが本当に COM20 に割り当てられていると、そのポートを使えません。

### 5.2 自動検出が接続先を確かめない

自動検出は COM20 から COM3 まで順に開いてみて、**最初に開けたポートを使う**だけです。USB の VID/PID や本体からの応答は確かめていません。

- Bluetooth の仮想 COM ポートなど、番号が大きくて開けるポートがほかにあると、そちらを選んでしまいます。その結果、20 秒待ったあとに「Communication device is not connected.」になります。
- COM1 と COM2 は自動検出の対象外です。

### 5.3 Write を最初に押しても書き込まれない

`Button2_Click`（Write）は、`PortName == "COM20"` のときは `Open_port()` を呼ぶ**だけ**で、書き込みの処理（`else` の側）に進みません。起動したあと、または自動検出の状態に戻ったあとに最初に Write を押すと、ポートを見つけるだけで何も書き込まず、メッセージも出ません。もう一度押すと書き込みが始まります。

一方 `Button1_Click`（Read）は、自動検出のあとで改めて条件を確かめているので、1 回押せば読み出しまで進みます。

### 5.4 通信が途切れると固まる

最初の応答のあと `ReadTimeout = -1`（無制限）にしています。読み出し中にデータが途切れたり、書き込み中に `r` が返ってこなかったりすると、**いつまでも待ち続けます**。通信は UI スレッドで同期的に行っているので、ウィンドウ全体が応答しなくなります。強制終了するしかありません。

### 5.5 受信の終わりを末尾の1文字だけで判定している

読み出しでは、受け取った文字列全体の**最後の1文字**が `/` かどうかだけを見ています。`/` のあとに1バイトでも続けて届くと、受信が終わりません（5.4 と合わせて固まります）。

### 5.6 読み出しのエラー表示がまぎらわしい

- 読み出しの処理（`Button1_Click`）の中で起きた例外は、原因に関係なく「Communication device is not connected.」と表示されます。たとえば、最初の応答を 20 秒待ってもタイムアウトしたときです。
- 一方、受け取ったデータの解析エラーは `ReadTextDataFile` の中で処理されます。そこで「The error occurred while reading the file.」を表示したあと、**読み出しの処理はそのまま続き、「Read completed.」も表示されます**。表には途中まで反映されたデータが残ります。

### 5.7 一時ファイルの扱い

- `verif.fmp` は**カレントディレクトリ**に作られます。
- 作る処理（`File.CreateText`）は例外処理の外にあります。カレントディレクトリに書き込めない場合（Program Files の中から起動したときなど）は、例外が処理されずにアプリが異常終了するおそれがあります。
- `verif.fmp` を削除するのは読み出しが成功したときだけです。失敗すると残ります。

### 5.8 書き込みを確かめていない

書き込みのあとに読み戻して比べる処理も、チェックサムもありません。本体側で値が壊れても、PC 側では気づけません。`verif`（verify の略と思われる）という名前は、読み出しで使う一時ファイルの名前にすぎません。

### 5.9 マップ番号の表示

マップ番号は、受け取った文字の**文字コードを10進で**表示しています。本体は生のバイト値で番号を送っているので問題は起きていません（[4.4 節](04-serial-protocol.md#マップ番号は生のバイト値)）。ただ、実装として素直とは言えません。0x80 以上の値は ASCII 変換で `?`（63）に化けます。

## ファイルまわり

### 5.10 行や値が足りないファイルを読むと、前の値が残る

`ReadTextDataFile` は、ファイルにあるセルだけを上書きします。行が 30 より少ない、または値が 21 個より少ないファイルを読むと、**足りない部分のセルには前の値がそのまま残ります**。エラーも警告も出ません。

### 5.11 範囲外の値を警告なしで丸める

読み込むとき、141 以上は +40、1〜59 は −40 に、警告なしで丸めます。手で編集したファイルの誤りに気づけません。

### 5.12 0 が1つでもあるとレブリミット扱いになる

ある列のどこかに `0` が1つでもあると、その列がレブリミットの位置とみなされます。列の 21 個すべてが 0 かどうかや、それより上の列もすべて 0 かどうかは確かめていません。

### 5.13 読み込むときはレブリミットの下限を確かめない

画面上で設定できるのは 9000〜15000 rpm ですが、ファイルを読み込むときは下限を確かめていません。極端な例として、先頭の列（500 rpm）に `0` があると `rpm_cell = -1`、`rev_limit = 0` になります。

### 5.14 リミットより上の値が表に残る

レブリミットを下げても、リミットより上の列の値は表の中に残ります。出力するときだけ `0` になります。リミットを上げ直すと、見えなくなっていた古い値がまた有効になります。意図した動作の可能性もありますが、気づきにくい点です。

## UI まわり

### 5.15 範囲外の警告文が少しずつ違う

Batch editing では `Ran over setting range.`（ピリオドあり）、Single editing では `Ran over setting range`（ピリオドなし）です。動作には影響しません。

### 5.16 使われていないフォームがある

`Form3` は中身が空で、どこからも呼ばれていません。`Form2` のラベルのクリックハンドラも中身が空です（URL のラベルをクリックしても何も起きません）。
